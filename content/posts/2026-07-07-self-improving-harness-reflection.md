最近看 self-improving-harness，最大的感受不是某一个具体方法有多巧，而是它让我重新意识到：做 Agent 研究，很多时候真正重要的不是一开始就让模型显得很聪明，而是要先把一个可靠的反馈系统搭起来。

如果没有好的评测，后面很多事情都会变得很虚。

模型看起来变强了，可能只是因为 prompt 更细了；任务成功率上去了，可能只是因为人类把中间步骤拆得太好了；某个 benchmark 上的数字变高了，也可能只是因为系统对那一类题目过拟合了。没有清楚的评测设计，就很难判断一个 agent 到底是真的能力提升，还是只是被外部工作流托了一把。

所以我现在越来越觉得，评测不是研究最后用来补充实验结果的东西，而是整个研究问题的地基。

## 评测先于改进

过去我会更自然地把注意力放在“怎么让 agent 做得更好”上，比如更好的规划、更好的记忆、更好的工具调用、更强的上下文管理。但看完 self-improving-harness 之后，我觉得这个问题应该往前挪一步：在讨论怎么改进之前，先要知道怎么判断改进。

一个好的评测方案，至少要能回答几个问题。

第一，当前系统到底弱在哪里。它是不会理解任务，还是不会探索环境；是工具调用不稳定，还是遇到错误之后不会恢复；是上下文太长之后丢信息，还是上下文太少的时候不会自己补全假设。

第二，改进之后，原来的问题有没有真的被解决。不能只是整体分数涨了一点，然后就说方法有效。更关键的是，那些原本暴露出来的薄弱点，在新的系统里是不是有了实质改善。

第三，这个改善有没有泛化。如果一个方法只是在原来的问题集合上表现更好，但换一批相似但不同的数据就掉下去，那它更像是在修补 benchmark，而不是提升系统能力。

这也是 held-in 和 held-out 数据集很重要的地方。

如果我们针对模型或者 harness 的某些薄弱部分做强化，验证的时候不能只看一个总分。held-in 数据集可以理解为原测评集中已经暴露出问题的那部分。我们当然希望强化之后，held-in 上的表现要明显提升，因为这说明原来被发现的问题确实被解决了。

但只看 held-in 是不够的。

还需要 held-out 数据集。held-out 跟 held-in 不一样，它不是直接拿来被修的那一批问题，而是用来判断这个改进有没有更一般的效果。理想情况下，held-out 上的能力也应该变好，因为我们希望每一次改进都不是只修一个局部漏洞，而是让系统在某个维度上真的更强。

至少，held-out 的表现也应该基本持平。

如果 held-in 上涨了，但 held-out 明显下降，这其实是一个很危险的信号。它说明我们可能只是把系统调得更适合某一批已知问题，却损害了更一般的能力。表面上看，系统解决了原来的 bug；但从研究角度看，这种改进并不扎实，因为它没有证明自己能迁移到新的任务分布里。

所以一个好的 agent 改进，应该同时满足两个条件：它能修复已知弱点，也不牺牲未知任务上的表现。更好的情况是，它在 held-out 上也带来提升。这样我们才更有理由相信，系统不是记住了某些题，而是真的学会了某类能力。

## 为什么我会想到 Terminal 场景

这也影响了我之后选论文方向时对场景的判断。

如果要做 agent，当然可以选很多看起来更开放、更宏大的任务，比如浏览网页、使用软件、完成复杂办公流程，甚至让智能体在一个接近真实世界的环境里长期运行。这些方向很有吸引力，但它们也有一个问题：评测很难做干净。

任务是否完成，经常需要人类判断；中间过程是否合理，也很难定义；结果好不好，可能受环境、网页状态、账号权限、外部服务变化影响。这样的场景不是不能做，而是如果一开始就从这里切入，研究变量会变得非常多。

相比之下，terminal 是一个更适合做早期研究的场景。

terminal 任务有几个天然优势。

它有明确的输入输出。一个命令有没有执行成功，文件有没有被正确修改，测试有没有通过，输出是否匹配预期，这些都可以比较稳定地自动化检查。

它有可复现性。很多任务可以在隔离环境里重复运行，环境状态可以重置，失败也可以被记录和回放。

它也有足够复杂的决策空间。terminal 并不是简单的问答。agent 需要读文件、查目录、运行命令、理解报错、修改代码、再运行测试。它既有明确的评测信号，又保留了真实 agent 任务中的探索、规划和恢复能力。

所以如果我之后要选一个具体论文场景，terminal agent 可能是一个很好的入口。不是因为它最炫，而是因为它更容易把实验做扎实。

一个研究场景最重要的不是听起来有多大，而是能不能形成稳定的闭环：提出问题，设计改进，运行评测，分析失败，再继续迭代。terminal 恰好适合这个闭环。

## 少给上下文，让智能体自己做决策

另一个让我感兴趣的问题，是上下文和自主性的关系。

现在很多 agent 系统之所以能完成任务，其实有一部分原因是人类给了非常多的上下文。任务被拆得很细，步骤被写得很清楚，规则被提前列好，甚至错误处理方式也被写进 prompt 里。在这种情况下，agent 的表现当然会变好，但这里测到的未必完全是 agent 本身的能力。

有时候，我们测到的是人类设计 workflow 的能力。

如果我们想更直接地考察智能体本身的智力水平，也许就应该有意识地减少上下文，让它自己做更多决策。比如只告诉它目标，而不是告诉它每一步怎么做；只给它必要约束，而不是给它完整操作清单；让它自己判断该读哪些文件、该运行哪些命令、该如何从失败中恢复。

这样做的好处是，问题会更清楚地转移到 agent 本身。

它是否能理解目标？是否能主动探索？是否能发现缺失信息？是否能在信息不足时形成合理假设？是否能在失败后调整路线？这些能力，只有在 agent 拥有一定决策空间的时候，才会真正暴露出来。

如果人类把所有东西都安排好了，agent 只是按步骤执行，那它当然更安全，也更容易成功。但这个成功可能没有那么有研究价值。因为它绕开了最核心的问题：当环境不完整、任务不确定、步骤没有被提前写好时，agent 到底能不能自己想明白下一步该做什么。

## 自主性越高，边界问题越明显

但这件事不能只往一个方向推。

让 agent 做更多决策，确实可以更好地测量它的能力；但一旦决策空间变大，边界问题也会跟着出现。

在 terminal 里尤其明显。一个 agent 如果只能读文件、运行测试、修改指定目录里的代码，风险还比较可控。但如果它可以自由执行命令、安装依赖、访问网络、删除文件、修改配置，事情就完全不一样了。

自主性越高，安全问题越真实。

这并不只是“模型会不会作恶”的问题。更多时候，风险来自目标不清楚、环境理解错误、工具使用不当，或者模型为了完成一个局部目标采取了过度激进的行动。比如它可能为了让测试通过而删掉测试，可能为了清理环境而误删重要文件，也可能在没有理解上下文的情况下修改了不该改的东西。

所以这里会出现一个张力。

如果给 agent 太少的自由度，评测会变得不真实，因为它只是在执行人类安排好的流程。如果给 agent 太多自由度，评测又会变得危险，因为它可能越过我们原本没有意识到的边界。

这意味着 agent 研究不能只问“怎么让它更自主”，还要问“应该允许它在哪些范围内自主”。

好的 harness 不只是用来提升能力的，也应该是用来定义边界的。它要告诉 agent 可以做什么、不可以做什么；哪些操作需要确认，哪些操作可以自动完成；哪些资源可以访问，哪些资源必须隔离；出现不确定情况时，是继续探索，还是停下来请求外部判断。

某种意义上，harness 是 agent 能力和安全之间的接口。

## 我现在对自己研究方向的理解

所以这篇文章给我的启发，最后可以收束成几个判断。

第一，评测非常重要，而且应该被放在研究设计的最前面。没有好的评测，就没有可靠的改进。

第二，terminal 是一个值得优先考虑的研究场景。它足够真实，也足够可控；有复杂的决策过程，也有相对清晰的自动化评测信号。

第三，减少上下文、增加 agent 自主决策，是一种更直接测量智能体能力的方式。它能把问题从 prompt 和 workflow 的设计，更多转移到 agent 本身的推理、规划和探索能力上。

第四，这种自主性必须有边界。agent 做的决策越多，安全问题越不可避免。研究的重点不应该只是把 agent 放出去，而是设计一个既能暴露能力、又能控制风险的环境。

第五，任何针对薄弱点的强化，都必须同时看 held-in 和 held-out。held-in 用来确认原来的问题是否被解决，held-out 用来确认这个解决方案是否有泛化性。真正好的改进，不应该只是让系统在已知问题上变好，而应该让它在更一般的任务上也更强，至少不能明显变差。

这样看，self-improving-harness 对我的意义不只是一个具体方法，而是一个研究视角：不要把 agent 能力看成孤立的模型输出，而要把它放进一个完整系统里理解。这个系统包括任务环境、评测设计、反馈闭环、上下文分配、工具权限和安全边界。

模型当然重要。

但对 agent 研究来说，真正决定我们能不能把问题做清楚的，可能是模型之外的那一整套东西：我们怎么测它，怎么暴露它的弱点，怎么验证改进，怎么让它自主，又怎么在自主性之外画出边界。

这也是我现在觉得 terminal agent 值得做的原因。它不是最大的问题，但可能是一个足够清楚的问题。对科研来说，清楚有时候比宏大更重要。
