最近看了 Orion 这篇文章，标题是 *Towards Lab Automation with Computer-Using Agents*。它的场景是生物医学图像分析，比如操作 CellProfiler、QuPath、Napari，完成细胞分割、病理切片分析和高通量图像数据探索。

但我觉得这篇文章最有价值的地方，不只在生物学本身。

生物学更像是一个非常好的例子：它暴露了很多垂直行业里真实存在的问题。很多行业的核心工作并不是纯代码，也不是纯文本，而是依赖专业 GUI 软件、人工调参、视觉检查、文件流转和领域指标判断。

比如：

- 生物图像分析里，要用 CellProfiler 或 QuPath 看图、调参、选 ROI。
- 工业设计里，要操作 CAD/CAE 软件，检查模型、设置参数、跑仿真。
- 金融风控里，可能要操作内部系统、导出表格、交叉核对指标。
- 医疗影像里，要浏览 DICOM、标注病灶、调整窗宽窗位。
- 地理信息分析里，要操作 GIS 软件、选图层、做空间分析。
- 芯片设计里，要用 EDA 工具检查版图、跑验证、看波形。

这些场景有一个共同点：**关键工作流被锁在 GUI 软件和领域经验里**。单纯调用 API 不够，单纯让模型点鼠标也不够。

Orion 给我的启发是：垂类 Computer Use Agent 的重点，不是“让 AI 会操作电脑”，而是“让 AI 进入一个领域工作流，并且让这个工作流可验证、可复用、可长期运行”。

## 第一种范式：Terminal + GUI 双通道

Orion 不是只靠 GUI 操作完成任务。它同时使用 terminal 和 GUI。

Terminal 负责代码执行、文件管理、批量处理、统计分析和结果保存。GUI 负责操作那些很难通过 API 访问的软件界面，比如图像查看、参数调节、ROI 选择、视觉质控。

这个结构可以推广到很多垂类场景。

对于一个垂类 Agent 来说，terminal 和 GUI 不是替代关系，而是互补关系：

- Terminal 适合规模化、结构化、可脚本化的部分。
- GUI 适合视觉化、交互式、软件封闭或 API 不完整的部分。

很多行业软件都是 GUI-first 的。它们可能有部分 API，但真正的专家工作流仍然发生在界面里。这个时候，GUI Agent 的作用不是炫技，而是补上“代码够不到的那一层”。

所以第一个范式是：

**用 terminal 处理规模，用 GUI 接入专业软件。**

## 第二种范式：把低级操作变成领域动作

通用 Computer Use 的底层动作是点击、输入、滚动、拖拽、截图。但垂类 Agent 不能停在这一层。

在生物学里，同样一个拖拽动作，可能是在 QuPath 里框选病理 ROI。

在 CAD 里，同样一个点击，可能是在选择约束、切换视角、修改草图。

在 GIS 里，同样一个缩放，可能是在检查不同尺度下的空间分布。

在医疗影像里，同样一个滑动，可能是在浏览 CT 切片序列。

底层都是 GUI 操作，但语义完全不同。

所以垂类 GUI Agent 需要把低级动作封装成领域动作 primitive。它不应该只知道“点击坐标”，而应该知道“我正在选择 ROI”“我正在调整阈值”“我正在检查仿真结果”“我正在切换图层”。

这是从通用 Computer Use 走向垂类 Agent 的关键一步。

通用 CU 解决的是：

> 怎么点？

垂类 CU 要解决的是：

> 为什么点？点完之后在领域流程里意味着什么？

## 第三种范式：从过程验证走向结果验证

这是我觉得最重要的一点。

普通 GUI 自动化很容易停留在过程验证：

- 页面打开了吗？
- 按钮点了吗？
- 表单提交了吗？
- 文件下载了吗？

但在垂类任务里，这些都只是低级成功。真正的成功要看领域结果。

在生物图像分析里，不是 CellProfiler 跑完就算成功，而是要看细胞有没有分对、计数是否接近 ground truth、阳性率是否合理。

这个逻辑可以推广到其他领域：

- CAD/CAE 里，不是仿真软件打开了就算成功，而是网格质量、边界条件、仿真结果是否合理。
- 金融分析里，不是报表导出了就算成功，而是指标口径是否正确、数据是否对账。
- 医疗影像里，不是标注工具保存了就算成功，而是病灶区域是否合理、测量值是否符合专家标准。
- GIS 里，不是图层加载了就算成功，而是空间分析结果是否符合地理约束。
- EDA 里，不是版图工具运行了就算成功，而是 DRC/LVS 是否通过、时序是否收敛。

这和编程很像。编程 Agent 不能只看代码有没有运行，而要看编译是否通过、测试是否通过、输出是否符合预期。

垂类 GUI Agent 也是一样。不能只看界面有没有操作成功，而要看操作产生的领域结果是否正确。

所以第三个范式是：

**给 GUI 操作建立领域级测试。**

这可能是垂类 Agent 能不能真正落地的分水岭。没有领域验证，它只是会操作软件；有了领域验证，它才可能完成专业任务。

## 第四种范式：Skills 不是点击脚本，而是领域 SOP

Orion 里有 self-evolving skill learning。这个部分如果只理解成“Agent 学会了操作软件”，就有点浅。

我觉得 skills 的重点不是保存一串点击步骤，而是沉淀可复用的领域工作流经验。

一个好的 skill 应该包含：

- 适用场景
- 操作流程
- 参数选择
- 常见失败模式
- 质控方法
- 输出格式
- 验证标准
- 后续分析方式

在生物学里，这可能是“核质转位分析怎么做”“whole-slide pathology 怎么导航和选 ROI”。

在 CAD 里，这可能是“某类零件的仿真前处理流程”。

在金融里，这可能是“某类风险指标的报表抽取和对账流程”。

在医疗影像里，这可能是“某类病灶的标注和测量流程”。

所以 skill 不是 GUI 宏，而是领域 SOP。

它记录的不只是“怎么点”，而是“这类任务应该怎么做”。

这是垂类 Agent 可复用性的来源。

## 第五种范式：文件系统作为长流程记忆

很多 GUI-heavy 垂类任务都不是短任务，而是长流程。

Orion 里提到，通过把中间结果外部化到文件系统，可以支撑数百步连续动作。这个点很重要。

因为真实工作流往往会产生大量中间产物：

- 原始文件
- 中间表格
- 软件工程文件
- 配置文件
- 截图
- 日志
- 导出结果
- 可视化图
- 报告草稿
- skill 文档

如果所有东西都塞进模型上下文，长流程一定会失控。文件系统实际上承担了长期记忆、状态同步和审计记录的作用。

对于垂类 Agent 来说，文件系统不是附属物，而是系统架构的一部分。

它让 terminal 和 GUI 可以共享状态，也让任务可以恢复、复查和复用。

所以第五个范式是：

**把中间过程文件化，让 Agent 的工作可恢复、可审计、可接续。**

## 第六种范式：主控 Agent + GUI 子 Agent

Orion 还有一个结构值得注意：它不是让一个 Agent 从头到尾既做全局规划，又沉入 GUI 操作细节，而是由主控 Agent 管全局，GUI subagent 负责局部界面任务。

这个设计很适合垂类 GUI 场景。

因为 GUI 操作很消耗上下文。它充满截图、坐标、界面状态、局部错误和反复尝试。如果主 Agent 一直陷在这些细节里，很容易丢掉整体任务目标。

更合理的方式是：

- 主控 Agent 理解任务目标、拆解流程、管理文件和结果。
- GUI 子 Agent 负责某个明确的软件操作任务。
- GUI 子 Agent 完成后，把文件、截图、日志和结果摘要交回主控。
- 主控再决定下一步。

这类似一个项目经理加专业操作员的结构。主控不需要记住每一次点击，但需要知道每个阶段产出了什么、是否通过验证、下一步怎么走。

所以第六个范式是：

**主 Agent 管工作流，GUI Agent 管局部软件操作。**

## Orion 作为一个例子，而不是唯一答案

回到 Orion。它的场景是生物图像分析，但它展示的不是一个只能用于生物学的方案，而是一种垂类 Computer Use Agent 的系统形态。

这个形态可以概括为：

**通用 Computer Use 底座 + 垂类 GUI primitive + 领域结果验证 + 可复用 skills + 文件系统长记忆 + 主控/子 Agent 分工。**

这里面，通用 CU 底座解决“能不能操作电脑”的问题。

垂类层解决“操作是否符合专业工作流”的问题。

验证机制解决“结果是否正确”的问题。

skills 解决“经验能否复用”的问题。

文件系统解决“长流程能否持续”的问题。

多 Agent 分工解决“复杂任务是否会被 GUI 细节拖垮”的问题。

这套范式并不局限在生物学。只要一个行业满足下面几个条件，就很适合用类似方式做垂类 Agent：

- 核心软件是 GUI-first，API 不完整或不好用。
- 工作流依赖人工调参和视觉检查。
- 任务会产生大量中间文件和结果。
- 有明确的领域评价标准。
- 专家经验可以沉淀成 SOP。
- 流程较长，不能靠一次短对话完成。

生物图像分析只是一个很典型的例子。

## 我对这个方向的理解

看 Orion 之后，我对 Computer Use 的理解有一点变化。

以前容易把 Computer Use 理解成一个通用能力：模型能看屏幕，能点按钮，能输入文字，能完成电脑任务。

但在垂类场景里，真正有价值的不是这个底层能力本身，而是它和领域工作流结合之后产生的系统能力。

也就是说，垂类 Agent 的壁垒不一定在“鼠标点得更准”，而在：

- 是否理解领域软件
- 是否知道关键操作的业务语义
- 是否能验证结果
- 是否能沉淀流程经验
- 是否能稳定跑完长任务
- 是否能把 GUI 和代码结合起来

Orion 的启发在这里。

它告诉我们，GUI-heavy 的垂类 Agent 不应该只是通用 Computer Use 套一个行业 prompt。更合理的实现方式，是把 GUI 操作纳入一个完整的、可验证的、可复用的领域工作流系统。

如果用一句话总结：

**垂类 Computer Use Agent 的重点不是让模型会操作界面，而是让界面操作成为专业工作流中可验证、可沉淀、可长期运行的一环。**
