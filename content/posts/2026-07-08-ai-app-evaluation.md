最近一直在想一个问题：一个 AI 应用上线以后，到底该怎么评？

很多时候，我们会很自然地先看一些技术指标，比如幻觉率、准确率、DPO 数据、Reward Model 有没有偏。但真正放到业务里，我觉得第一件事不是先给问题贴技术标签，而是先问几个更朴素的问题：

用户用得好吗？  
业务有没有变好？  
如果哪里不好，我们能不能查出来为什么不好？

这才是评测最该解决的事。

之前我也会问：一个业务 badcase 出现以后，怎么判断它是幻觉、DPO 数据问题，还是 Reward Model 偏差？

但后来觉得，这个问题问得有点太早了。真实业务里的问题，很多时候没法一上来就归到某个技术概念里。更合理的问法应该是：

业务表现不好时，我们怎么一步步排查？

我觉得可以先把 badcase 分成两类。

第一类，是边界很清楚的问题。

比如引用了不存在的政策，输出的 JSON 格式错了，没有调用本来必须调用的工具，或者检索没有找到正确文档。

这类问题就比较好办，可以直接翻译成技术问题：事实错了、格式约束失败、工具调用失败、RAG 召回失败。

第二类，是一开始说不太清楚的问题。

比如用户觉得不专业，回答没说到点上，转化没有提升，体验不够顺。

这类问题就不能一上来就说它是幻觉，或者是 DPO、RM 的问题。它可能只是标准没说清楚，也可能是 prompt 没写明白，知识库没给对材料，或者参数设置让模型变得太随机。

所以我的理解是：清楚的问题，直接翻译成技术问题；模糊的问题，先从最容易改、成本最低的地方查起，再慢慢往模型和数据里面走。

一个比较朴素的排查顺序是：

第一步，先确认它是不是真的错。

有时候不是模型错，而是大家对“好”的理解不一样。比如“回答要专业”这句话就很模糊。什么叫专业？是术语准确，语气正式，不能夸大，还是要引用依据？

如果这个标准不说清楚，不同人就会给出不同判断。

第二步，看问题能不能复现。

同一个问题多问几次还错吗？  
把 temperature 降低还错吗？  
加上知识库资料还错吗？  
换一个 prompt 还错吗？  
换一个模型版本还错吗？

如果只有随机采样时才错，可能是参数问题。  
如果加了正确资料以后就好了，可能是知识或 RAG 问题。  
如果怎么问都错，才继续往模型能力、训练数据、偏好数据里查。

第三步，把业务问题翻译成技术问题。

比如：

| 业务表现 | 技术上可能是什么 |
|---|---|
| 编造产品功效 | 事实错误 / 幻觉 |
| 没按流程回答 | 指令遵循问题 |
| 说得很顺但结论错 | 推理或偏好问题 |
| 明明能回答却拒答 | 安全策略过强 |
| 回答很长但没用 | DPO 或 RM 偏好问题 |
| 引用资料不对 | RAG 问题 |
| 格式不对 | Prompt 或 SFT 问题 |

这一步很重要。业务里说“用户觉得不好”，技术团队其实很难直接修。必须把它拆得更具体一点。

## Reward Model：别只看模型，也要看“裁判”

如果前面说的是 badcase 怎么查，那 Reward Model 这一块，其实是在说另一个问题：

有时候模型越训越偏，不是因为它完全不会，而是因为奖励信号在把它往错误方向带。

Reward Model 可以简单理解成一个“自动裁判”。它看一个回答，然后给一个分数。分数越高，说明它越觉得这个回答好。

但裁判也可能看走眼。

比如用户问：

“这个产品能不能治疗高血压？”

回答 A：

“不能。这个产品不是药品，不能宣称治疗疾病，也不能替代医生诊断和药物治疗。”

回答 B：

“可以，它能够有效改善高血压问题，长期使用有助于恢复健康状态。”

从业务和合规角度看，A 明显更好。但如果 Reward Model 给 B 更高分，因为 B 更自信、更完整、更像销售话术，那这个 RM 就有问题。

所以评 RM，不是看它会不会打分，而是看它这个“裁判”准不准。

还有一点很重要：Reward Model 不是一个模型走天下。

不同业务里，“好回答”的标准是不一样的。

医疗、金融、法律这些场景，安全和合规最重要。回答可以保守一点，但不能编造和乱承诺。

客服场景里，用户问题有没有被解决、流程有没有走对，可能更重要。

营销场景里，表达和转化很重要，但不能为了成交去夸大。

代码场景里，能不能跑、测试能不能过，可能比语言写得漂不漂亮更重要。

所以评 RM 之前，得先想清楚：

这个场景里，我们到底希望它奖励什么？  
什么是底线？  
什么是加分项？  
什么是绝对不能鼓励的？

如果这些没想清楚，RM 学到的东西就会很混乱。它在一个场景里学到的“好”，换到另一个场景里可能就是风险。

那 RM 怎么评呢？

第一，看它能不能选对。

准备一批人工已经判断好的回答对，一个好答案，一个坏答案。然后看 RM 能不能把好答案排在坏答案前面。

也就是问：

人觉得 A 比 B 好，RM 是不是也这么觉得？

第二，专门测它会不会被表面特征骗到。

比如短但正确的回答，和长但错误的回答，它选谁？  
朴素但正确的回答，和华丽但错误的回答，它选谁？  
纠正用户错误的回答，和顺着用户说的回答，它选谁？  
谨慎正确的回答，和武断错误的回答，它选谁？

如果 RM 总是偏向后者，那模型就会越来越会“讨好裁判”，但不一定真的服务用户。

第三，把真实 badcase 拿回来测。

线上出了一个坏回答，就拿这个坏回答和人工改好的答案一起给 RM 打分。

如果 RM 给坏回答更高分，就说明问题不只是模型生成错了，奖励信号也可能在帮倒忙。

说白了，评 RM 就是在问：

这个奖励信号，到底有没有把模型往我们想要的方向带？

## Rubric：先把“什么叫好”说清楚

Rubric 这一块，我其实还没有想得特别深。但有一点很明确：如果大家不先说清楚“什么叫好”，后面的评测、RM、数据飞轮都会很容易跑偏。

很多词听起来都对，比如“不专业”“没帮助”“不安全”。但这些词太大了。不同人理解不一样，最后标注也会不稳定。

所以 rubric 最重要的作用，不是做一张很复杂的表，而是让大家先对齐标准。

比如客服场景，至少要说清楚：

有没有解决用户问题？  
有没有编造政策？  
有没有按业务流程走？  
有没有给出明确下一步？  
有没有踩到合规红线？

不同场景，重点也不一样。

医疗、金融、法律场景，安全和合规应该放在前面。  
营销场景，表达和转化重要，但不能夸大承诺。  
代码场景，能不能运行、测试能不能过，可能比语言是否漂亮更重要。

所以我现在对 rubric 的理解比较朴素：

它就是把“我觉得好/不好”，变成“我们知道为什么好/不好”。

一个基本的 rubric 至少要做到三件事。

第一，标准要来自具体业务，不要只写“准确、有帮助、安全”这种大词。

第二，最好能拆几个维度，比如事实准确、业务合规、任务完成、证据一致、表达清晰。不要只给一个总分，因为只看总分，很难知道到底哪里出了问题。

第三，要有一票否决项。比如编造关键事实、违反合规红线、泄露隐私、引用不存在的资料。这些问题不能因为回答很流畅、很礼貌就被抵消。

rubric 不一定一开始就很完美，但至少要让人审、自动评测、RM 和 badcase 归因用的是同一套语言。

否则大家都说自己在优化模型，但优化的可能根本不是同一个东西。

## 轻量评测和用户评测：一套用来日常迭代，一套用来看方向

Rubric 说的是“什么叫好”。但真正做评测时，还会遇到另一个问题：评测体系要不要只有一套？

我觉得不应该。

如果评测太轻，跑得快，但可能离真实用户太远。  
如果评测太重，更接近业务，但跑不动，也不适合每次改动都拿来调。

所以更合理的是分成两层。

第一层是轻量评测，更像开发过程里的 validation set。

它不用完美代表所有用户，主要是快速判断：

这次改动有没有变好？  
之前的问题有没有修回来？  
有没有引入新的问题？

这套评测应该小一点、稳一点、便宜一点，最好能高频跑。它可以覆盖历史 badcase、高频问题、核心流程、高风险合规样本、RAG 和工具调用、格式检查等等。

它回答的是：

改 prompt 有没有用？  
换 RAG 策略有没有变好？  
换模型有没有回退？  
之前修过的问题有没有复发？

第二层是面向用户的评测，更像 test set 或业务验收。

它不应该天天拿来调参，而是用来判断：

这个版本是不是真的对用户有帮助？  
是不是真的对业务有价值？

它更关注用户价值，比如问题解决率、满意度、转人工率、完成时长、投诉率、转化率、留存、成本下降、风险降低。

这套评测可以在版本发布、灰度、A/B 前后使用。

两层评测的关系大概是：

轻量评测看技术上有没有变好。  
用户评测看这个变好有没有用户意义。  
线上指标看它最后有没有变成利润、留存、成本或风险收益。

只做轻量评测，可能会出现“指标涨了，但用户没感觉”。  
只做用户评测，又会反馈太慢，而且很难知道具体该修哪里。

所以这两套要配合起来。

轻量评测保证日常迭代跑得动，用户评测保证方向别跑偏。最后再用线上 A/B 去看是不是真的带来了业务收益。

这也能接上数据飞轮。

线上用户问题先进入用户评测，沉淀出典型 badcase，再抽象成轻量回归样本。这样下一次改 prompt、改 RAG、换模型、补数据时，就能快速验证老问题有没有被修好，也有没有重新出现。

## 最后

我现在越来越觉得，AI 评测不是一次性给模型打个分，而是一套持续改进的方法。

先看业务里用户到底有没有被服务好。  
遇到 badcase，不急着贴技术标签。  
能清楚定义的，直接翻译成技术问题。  
说不清楚的，先从低成本的地方查。  
如果涉及奖励信号，就看看 Reward Model 这个“裁判”准不准。  
如果要让评测稳定，就先用 rubric 把“什么叫好”说清楚。  
最后，用轻量评测支持日常迭代，用用户评测和线上指标确认方向没有跑偏。

说到底，评测不是为了证明模型有多强，而是为了让业务里的每一次问题，都能被看见、被解释、被修掉，然后变成下一轮优化的材料。
